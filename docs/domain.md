# Домен: перевод SQL между диалектами

## Постановка

Даны два SQL-движка A и B со своими диалектами, общий набор исходных таблиц и распределение допустимых состояний данных. Скрипт s на диалекте A читает исходные таблицы и создает выходные таблицы O(s). Нужен переводчик T такой, что для состояний данных D из распределения

```math
B\big(T(s),\,D\big)[t] \;\equiv\; A\big(s,\,D\big)[t] \qquad \forall\, t \in O(s),
```

где ≡ - равенство мультимножеств строк после нормализации типов. Хорошее решение сохраняет семантику и на граничных данных: NULL, пустые таблицы, конец месяца, ничьи при сортировке.

Почему это трудно. Эквивалентность программ в общем виде алгоритмически не проверяется, поэтому качество измеряют исполнением. Диалекты расходятся не только синтаксисом, но и семантикой: `greatest` и `concat` по-разному обрабатывают NULL, по-разному сортируются NULL при `DESC`, по-разному нумеруются дни недели, в Trino нет временных таблиц и `UPDATE ... FROM`, в Greenplum нет `MERGE` и лямбд.

## Классические подходы

| Подход | Идея | Сильные стороны | Слабые стороны | Известные оценки |
|---|---|---|---|---|
| Правиловый транспайлер ([SQLGlot](https://pypi.org/project/sqlglot/), jOOQ, SQLines) | Разбор в AST и генерация в целевом диалекте по правилам | Быстро, детерминированно, без модели | Специфичный DDL, состояние скрипта, функции без прямого аналога | По данным CrackSQL, SQLGlot на PG → MySQL - 70.97% совпадения результатов |
| LLM без адаптации | Модель переписывает запрос по инструкции | Знает много функций, понимает намерение | Нестабильна, ошибается на редком синтаксисе | В [PARROT](https://arxiv.org/abs/2509.23338) (NeurIPS 2025) LLM в среднем ниже 38.53% |
| Гибрид правил и LLM ([CrackSQL](https://dbgroup.cs.tsinghua.edu.cn/ligl//papers/SIGMOD25-CrackSQL.pdf), SIGMOD 2025) | Правила там, где справляются; LLM - только на проблемных фрагментах, с проверкой | Лучший из известных результатов | PostgreSQL, MySQL, Oracle, без Trino | +3.22…21.95 п.п. к SQLGlot и +7.69…34.93 п.п. к GPT-4o по совпадению результатов |
| Оценка по нескольким базам ([Zhong, Yu, Klein, 2020](https://aclanthology.org/2020.emnlp-main.29)) | Сравнивать результаты на наборе сгенерированных баз | Снимает ложные срабатывания одной базы | Нужен генератор данных | Основа для четырех состояний данных в нашей метрике |

## Baseline

SQLGlot 30.27.0, `transpile` по операторам скрипта (`case/ways/baseline`). Результаты на train (локальный PostgreSQL, эталоны парным рендером; финальные цифры - на стенде):

| Направление | Score | Комментарий |
|---|---|---|
| trino2gp | 0.116 | 250 примеров, полный замер исполнением |
| gp2trino | ≤ 0.024 | Офлайн-оценка: только в 6 из 250 переводов не осталось конструкций Greenplum |

Где baseline справляется и где нет (trino2gp, доля решенных по шаблонам):

| Шаблон | Score | Шаблон | Score |
|---|---|---|---|
| store_rank | 0.60 | category_monthly | 0.04 |
| last_order | 0.39 | calendar, contacts, fact | 0.00 |
| cohorts | 0.33 | loyalty, promo, rfm | 0.00 |
| daily_sales | 0.24 | stock_alerts, tags | 0.00 |
| payments | 0.15 | | |

Самые частые причины провала trino2gp: префикс каталога `iceberg.` остается в именах, свойства Iceberg превращаются в `USING 'PARQUET'`, `to_hex(md5(...))` переводится в несуществующий `encode`, `split` и `format_datetime` остаются без перевода, MERGE запрещен гейтом диалекта Greenplum.

Что остается в переводах gp2trino (из 250): `DISTRIBUTED` - 211, опции хранения `appendonly` - 175, `::` - 105, временные таблицы - 40, `age()` - 38, `md5` без `to_hex` - 34, `date_part` - 28, `to_char` - 25, `UPDATE ... FROM` - 21, `DELETE ... USING` - 19, DISTINCT ON - 18. Основная причина: SQLGlot не разбирает оператор с опциями хранения Greenplum и передает его как есть, поэтому внутри остаются вообще все конструкции.

Вывод для эволюции: запас огромный, а самые дешевые шаги видны сразу - снять физические опции Greenplum до разбора, убрать префикс каталога, перевести временные таблицы и `UPDATE ... FROM`. Дальше идет длинный хвост семантических различий, где окупаются LLM-фоллбэк и самопроверка.
