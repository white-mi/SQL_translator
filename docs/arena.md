# Арена: как она устроена и как на нее ложится наш кейс

Источник - архив арены, закрепленный по SHA-256 (см. [ADR 0001](adr/0001-arena-pin.md)).

Проверки самой арены (`uv run python -m evaluator.smoke`, `uv run pytest`, `uv run ruff check .`):

- в песочнице 4.11: smoke и 1633 теста ядра проходят;
- на своем ноутбуке 6.11 (WSL2, Ubuntu 24.04, ядро 5.15, Python 3.12.3): smoke проходит, ruff чистый, тесты ядра - 1625 прошли, 6 пропущены, 2 упали, оба в `tests/test_assets.py`;
- на VM 8.11 (Ubuntu 24.04, ядро 6.8, Python 3.12.3): smoke проходит; из `tests/test_assets.py` падают те же тесты, 1-2 из 31, число меняется от прогона к прогону. Остальные тесты ядра на VM не запускались.

Эти тесты проверяют, что публикация общих файлов замечает подмену файла во время копирования. Вероятная причина падений - грубые отметки времени файлов в обычном ядре Linux, а не особенность WSL: на VM 200 быстрых записей подряд дали только 28 разных mtime. Наш кейс публикацию общих файлов не использует, приемка на VM проходит 19/19.

## Роли

| Роль | Что делает | Зачем нужна |
|---|---|---|
| Агент подготовки | Превращает описание кейса в исполнимую метрику, проверяет ее и замораживает пакет | Метрика готова и неизменна до поиска, иначе эволюция подгоняется под измеритель |
| Оператор (студент) | Ставит зависимости, поднимает оценщики, выдает исследователям только разрешенные адреса и токены | Только оператор видит закрытые данные и итоговые private-результаты |
| Оркестратор | Планирует поиск, раздает направления, следит за лимитом, выбирает финалистов | Держит общую картину и воронку под точное число финалистов |
| Исследователи | В отдельных worktree предлагают кандидатов: гипотеза → изменение → замер | Параллельно проверяют независимые идеи и не мешают друг другу |
| Ревьюер | Проверяет кандидата перед финалом: сопоставимость замеров, подгонку, зашитые ответы | Высокий score не доказывает допустимость решения |
| Private-оценщик | Один раз оценивает замороженный набор финалистов и выбирает N лучших | Честная итоговая оценка на данных, которые поиск не видел |

Подготовка и поиск - отдельные запуски. Поисковый агент проверяет `preparation.md` и сам подготовку не запускает.

## Видимость данных

| Раздел | Что видит исследователь | От чего защищает |
|---|---|---|
| train | Все: скрипты, эталоны, ответы, статистику ошибок | Это материал для исследования и обучения |
| public | Только общий score кандидата | Не дает подгоняться под конкретные примеры: обратная связь есть, а деталей нет |
| private | Ничего, даже итоговой оценки | Защищает финальную оценку от любой утечки через обратную связь |

## Лимит, журнал, кривая

- **Лимит** - единственное ограничение поиска: число предложенных решений. Каждая версия, включая неудачные, занимает место. Токены и время измеряются, но поиск не ограничивают.
- **Журнал** (`evaluator.search`, SQLite) хранит каждое предложение: ID, родителей, неизменяемый снимок файлов, гипотезу и замеры. У неудачного решения тоже могут быть потомки.
- **Родословная** - граф «решение → родители»; одно решение может объединять несколько родителей.
- **Кривая эволюции** - лучший score в зависимости от номера решения; **AUC** - площадь под ней. AUC отличает быструю эволюцию от медленной даже при одинаковом финале. Арена строит кривую командой `evaluator.search curve`.

## Финализация и private

Переход к финалистам разрешен только после исчерпания лимита или явной команды человека. Арена проверяет это в коде: `finalize` сверяет журнал, а private-сервис - лимит и число финалистов K. Набор ровно из K кандидатов отправляется на private один раз; оценщик выбирает N лучших по метрике и ресурсам; результаты видит только оператор. Повторной попытки в той же серии нет, новую серию назначает только человек.

## Граница изоляции

Изоляция держится на правах доступа, а не на тексте промпта:
- кандидат исполняется в одноразовом контейнере: readonly-пакет, текущий вход через stdin, ответ через stdout; немодельный харнес запускается без сети;
- метрика - доверенный код оператора, исполняется в окружении оценщика и может читать данные своего раздела;
- исследователь работает в контейнере researcher: только train-workspace, общий журнал, API оценщиков и шлюз модели, без интернета, ключа провайдера, Docker socket и закрытых каталогов.

## Как на это ложится наш кейс

| Механизм арены | Как реализовано в SQLTR |
|---|---|
| Пакет метрики `kind: command` | `case/metric`: `score.py` читает пример из stdin, исполняет перевод на целевом движке и печатает `{"score", "statistics"}`. Пакет проходит `freeze` и `verify` арены |
| Немодельный харнес без сети | Решатель только переводит текст и к движкам не обращается; самопроверка - офлайн, парсером целевого диалекта |
| Падение кандидата останавливает серию | Харнес `sqltr-program` превращает падение в ответ-маркер, метрика ставит 0 (ADR 0008); baseline и потомки и так возвращают ответ при любой ошибке |
| Метрика в окружении оценщика | Оценщики - процессы на хосте VM, метрика ходит в PostgreSQL и Trino на 127.0.0.1; драйверы движков - в venv арены (`case/deploy`) |
| Изоляция исполнения | Перевод выполняется под непривилегированной ролью `sqltr_runner` в схемах с уникальными именами; писать можно только в `wrk_*` и `sandbox_*`, исходные таблицы только читаются (права в PostgreSQL и правила доступа Trino) |
| Сбой ≠ score | Ошибка перевода дает 0, сбой движка - ненулевой код выхода (ошибка проверки, а не оценка) |
| Ресурсы | Решатель без модели: токены 0, время измеряет runner. Кэш метрики по хешу перевода сокращает время оценщика и на выбор не влияет |
| Public и private | Генерирует оператор с секретными сидами; id примеров непрозрачны |

## Что проверено локально (4.11, `case/acceptance`, 19/19)

Арена закреплённой ревизии поднята в песочнице с настоящим Docker: три оценщика, журнал, runner-контейнеры, наша метрика на PostgreSQL. Подтверждено поведение, от которого зависит план:

- readiness отказывает без журнала и включает защиту private только в режиме `campaign`;
- лимит предложений проверяется журналом: лишнее `propose` отклоняется;
- train возвращает поэкзампларные ответы и `statistics` метрики; запрос обрабатывает примеры последовательно (~1.9 с на пример с метрикой на PostgreSQL);
- public отдаёт `{"status", "evaluation_id", "scores": [{"candidate_id", "score"}]}`, private - только `{"status"}`; оценки и победители лежат в `state-private/*/record.json` у оператора;
- private до `finalize` - HTTP 409, неверное K - 422, эти отказы попытку не тратят; после принятия другой пакет - 422, тот же пакет - прежний статус, в том числе после рестарта сервиса;
- падение кандидата на комплектном runner валит всю private-серию (`failed`, без оценок) - поэтому харнес ADR 0008;
- отказ движка валит серию громко: `failed`, без нулей и победителей;
- ничья по score решается временем решателя (`score-direction-known-tokens-asc-seconds-asc-id-asc-v2`): у одинаковых кандидатов победитель менялся между прогонами.

На VM 8.11 та же приемка прошла с настоящим Trino и обоими направлениями: 19/19 за 302 с ([отчет](../results/acceptance/vm-2026-11-08.json)). Полный train из 500 примеров через арену там же: кандидат со всеми верными переводами получает ровно 1.0 за 17 минут, baseline - 0.064 за 11 минут, как и без арены ([замер](../results/stand/full-train-2026-11-08.json)). Решатель в контейнере занимает ~0.6 с на пример.

## Отличия от арены

Свой харнес `sqltr-program` (ADR 0008) - это штатное расширение арены: оператор регистрирует сторонний образ до кампании. Образ исследователя с Hermes и шлюз модели тоже свои (ADR 0007, `case/researcher`): арена оставляет эту часть оператору, а ее `evaluator.gateway` рассчитан на вызовы решателя. Других отличий нет. Если сработает запасной путь (кампания по своей методологии, B-0.2), отличия будут перечислены здесь и в отдельном ADR.
