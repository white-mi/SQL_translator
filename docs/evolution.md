# Разбор эволюции

Заполняется по ходу кампании (черновик к ЧП2, итог к ЧП3). Данные: журнал `evaluator.search` (команда `export`), train-замеры из основной кривой. Проба подхода вне кампании - в [poc.md](poc.md), в эту эволюцию она не входит.

Состояние на 20.11 22:25 UTC: кампания `sqltr-c1` **завершена** - 30 предложений из 50, ранний стоп оператора на плато 1.0, финализация K=5 → public → private → победители N=3. Числа - из [итогового артефакта](../results/campaign/sqltr-c1-final-2026-11-20.json).

## Родословная

Линейная цепь baseline → cand-02 → … → cand-14 → cand-15 (в измерении на момент снапшота). Ветвлений нет: каждое следующее изменение строится на лучшем и диагностируется по разбивке ошибок train, которую возвращает train-сервис (`statistics` метрики: класс расхождения на пример). Это стратегия исследователя: закрывать самый массовый класс ошибок следующим кандидатом.

## Тупики

Полных тупиков (ухудшение кривой) пока нет. Ближайший - cand-07: замена DOUBLE → DOUBLE PRECISION не дала Δ (0.518 → 0.518): ошибка типа ушла, но открыла round(double precision, integer). Исследователь увидел это по разбивке и следующим кандидатом (cand-08) сменил цель замены на NUMERIC. Двухшаговая коррекция - пример пользы отрицательного результата: замер cand-07 был нужен, чтобы увидеть новый класс ошибки.

## Сопоставление с доменом

Классы, закрытые эволюцией, совпадают с разбором домена ([domain.md](domain.md)): расхождения PostgreSQL/Greenplum ↔ Trino на Iceberg группируются в (1) конструкции, не разбираемые транслятором, (2) функции без аналога, (3) типы и арифметика дат, (4) синтаксис UPDATE/MERGE и агрегации. Исследователь переоткрыл ту же карту классов снизу, по ошибкам исполнения.

## Вклад компонентов

Абляции (только правила / правила + постобработка / полный конвейер) не проводились - на ЧП2 решатель еще меняется. Косвенная оценка: вклад cand-02 (устойчивость разбора) - половина всего роста (0.064 → 0.366 из 0.706); остальные правила дают близкие шаги по своим классам. K финалистов и абляции - после исчерпания лимита.

## Финализация

Исследователь дошел до 1.0 на 30-м предложении и перестал предлагать (холостые ходы); оператор записал ранний стоп **двойным свидетельством** - `stop` в журнале + `search-control/stop.json` с тем же digest/причиной и source_ref (арена сверяет их при допуске private). Финалисты K=5 - топ-5 train (cand-26…30); public и private оценивала арена; private одноразовый, победители N=3 = cand-30, cand-29, cand-27 (ничья cand-27/cand-28 на 0.955 решена временем решателя: 121.0 с против 126.9 с). Итог private-оценщика (только оператор): `state-private/<dataset-digest>/record.json`.

## Что я понял о задаче

- Половина провалов baseline - не «плохой перевод», а отказ разбора: пайплайн, падающий на первом неразобранном операторе, теряет весь скрипт. Устойчивость разбора важнее качества правил.
- Метрика по 4 состояниям данных отсеивает «почти эквивалентные» перезаписи: NULL и пустые таблицы (s2, s4) ловят расхождения, невидимые на обычных данных.
- Разбивка ошибок train - главный сигнал для исследователя: каждый шаг формулируется как «класс X - N примеров → правило для X».
- Мир из ~30 перечислимых классов эволюция закрывает целиком (train/public/private = 1.0), но перенос за пределы генератора упирается не в количество правил, а в их ширину: все 6 holdout-провалов - правила, подогнанные слишком узко под паттерны шаблонов (вложенность `count_if(regexp_like(...))`, timestamptz в `GENERATE_SERIES`, новая форма интервалов). Это проект кампании v2: композиционные семейства, где такие вложенности встречаются в train.
- Остановка поиска - часть метода: плато на идеальном score легитимно, двойное свидетельство стопа (журнал + файл оператора) делает его проверяемым.
