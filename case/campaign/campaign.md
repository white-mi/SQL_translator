# Условия кампании (черновик к ЧП1)

Статус: черновик. Числа помечены как ориентир и фиксируются после замера на стенде (ЧП1) и подготовки по `prompts/prepare.md` арены. После старта поиска условия не меняются.

- Каталог кампании: `cases/sqltr/campaigns/sqltr-first-<дата старта>`
- Версия метрики: `sqltr-metric-v1` (заморожена до поиска командой `evaluator.prepare freeze`)
- Версии данных: train `seed 20261101, 250 семейств`; public и private - `operator/seeds.json`, по 100 семейств
- Состояния данных: s1-s4, генератор `sqltr/warehouse.py` той же ревизии
- Движки: PostgreSQL 16.4, Trino 483 + Iceberg (JDBC-каталог, локальное хранилище)
- Арена: архив с SHA-256 `18519eee87328febd8f3f7ea772705bdf2400fbd4610ff9cb05adcc3a8c8a687`
- Исследователь: Hermes в контейнере researcher арены; модель Claude Haiku 5.5, усилие Max
- Решатель основной кампании: харнес `sqltr-program` без модели (`network=none`), образ `sqltr-runner:1` с SQLGlot 30.27.0; падение кандидата = 0 на примере, а не сбой серии (ADR 0008)
- Разрешенные изменения: код решателя в `ways/<кандидат>/` (правила, обработка скрипта, самопроверка)
- Таймауты: оператор на скрипт 30 с, пример 240 с, команда метрики 600 с; решатель - 120 с на пример

## Лимит предложенных решений: ориентир 50

Почему столько:
- стоимость кандидата - сумма по примерам; в локальной приёмке арены (4.11) решатель в контейнере ~1.4 с, метрика ~0.4 с на PostgreSQL, train-запрос идёт последовательно; на Trino время замеряется на ЧП1;
- полный train проходит каждый кандидат: это основная кривая (см. «Сопоставимость замеров»); быстрые проверки на своих подвыборках (~150 примеров, ~5 минут) исследователь делает по желанию, public - только для претендентов в финалисты;
- кэш метрики по хешу перевода: потомок меняет переводы лишь части скриптов, остальные берутся из кэша;
- при 7-17 минутах на кандидата 50 кандидатов укладываются в 6-14 часов машинного времени, то есть кампания проходит за 2-4 дня вместе с работой исследователей;
- плато ожидаем после закрытия основных классов расхождений (их около 30), то есть в районе 30-40 решений; 50 оставляет запас.

## Сопоставимость замеров

Ключ сопоставимости арены - точное сочетание `split`, `dataset`, `subset`, `conditions`. Замеры с разными ключами в одну кривую не сводятся.

| Поле | Значения |
|---|---|
| `dataset` | `train-20261101-250`, `public-v1`, `private-v1` |
| `subset` | `all` - раздел целиком; свои подвыборки исследователь называет сам, в основную кривую они не входят |
| `conditions` | `sqltr-metric-v1-runner-1` |

`sqltr-metric-v1-runner-1` - это замороженный пакет метрики `sqltr-metric-v1`, образ кандидатов `sqltr-runner:1`, движки, состояния данных, таймауты и арена из списка выше. Хеш пакета (`metric.lock.json`) и digest образа записываются в `preparation.md`. Модель исследователя в условия проверки не входит, потому что решатель ее не вызывает, но она одна на всю кампанию.

- Основная кривая и AUC: `train / train-20261101-250 / all / sqltr-metric-v1-runner-1`, этот замер проходит каждый кандидат.
- Вторая кривая: `public / public-v1 / all / sqltr-metric-v1-runner-1`, по претендентам в финалисты.
- Если на стенде полный train займет больше 20 минут на кандидата, основной ключ до старта поиска меняется на фиксированную подвыборку train, а список ее примеров коммитится в `case/dataset/`.

## Учет ресурсов

- Решатель без модели: `solver_tokens = 0`, `solver_seconds` измеряет runner снаружи кандидата. При равном score арена ставит выше кандидата с меньшим временем решателя.
- Метрика без модели: `judge_tokens = 0`. Время оценщика записывается, но в ранжировании не участвует; кэш метрики сокращает только его.
- Токены и время исследователей (Claude Haiku 5.5 через прокси LiteLLM) записываются по каждому предложению для отчета о стоимости кампании. Лимитом поиска они не служат.

## Долгие прогоны

По `common/long-runs.md` арены:

- train запускается штатным `evaluator.train` отдельным заданием, которое переживает закрытие сессии исследователя; ID задания, конфигурация, прогресс и результаты лежат в каталоге кампании;
- срок ожидания считается по фактическому прогрессу: `осталось = прошло / готово × (всего - готово)` плюс 15%, без частого опроса;
- public и private ждут через `python -m evaluator.client wait`: он завершается и при `complete`, и при `failed`, а неизвестный статус разбирает оператор.

## Трекинг

MLflow в кампании не используется. Train-сервис сохраняет ответы по примерам, `statistics` метрики и ресурсы локально и отдает их исследователю через свой API, порядок кандидатов и родословную хранит журнал `evaluator.search`. Почему: решатель без модели, трейсов модельных вызовов нет, а лишний сервис на одной VM - лишний источник сбоев. Если MLflow понадобится (например, для модельного харнеса во второй кампании), он подключается новой версией условий до старта той кампании.

## Финализация

- Финалистов на private (K): 5
- Итоговых решений (N ≤ K): 3
- Правило выбора финалистов: score на public, разнообразие механизмов и ветвей родословной (например, правила по AST, обработка скрипта целиком, офлайн-самопроверка), отсутствие нарушений по ревью, устойчивость по направлениям, признаки переобучения (разрыв между train и public)
- Перед finalize каждый финалист проходит полный train и public без `candidate_fault`; копии одного механизма в финал не берём: ничью по score арена решает временем решателя, то есть шумом

## Запасной сценарий

Если прогон одного кандидата на public на ЧП1 займет больше 20 минут, основная кампания идет по направлению gp2trino, а trino2gp становится второй кампанией (бонус B-5.3). Если к 18 ноября арена не готова, кампания идет по своей методологии, максимально близкой к арене (B-0.2); отличия описываются в ADR и `docs/arena.md`.
