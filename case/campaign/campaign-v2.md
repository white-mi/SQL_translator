# Условия кампании v2: композиционный мир (черновик до подготовки)

Статус: кампания v2 запущена 2026-11-21. Условия зафиксированы: метрика заморожена (sha256 lock-файла - в preparation-заметках оператора), генератор и данные собраны. После старта поиска условия не меняются. Начинайте работу немедленно: первый ход - регистрация baseline (см. «Порядок работы»).

- Каталог кампании: журнал `/search/search.sqlite3` (запись кампании; каталог в чекауте арены не ведется)
- Версия метрики: `sqltr-metric-v2` (тот же пакет, новая заморозка)
- Версии данных: train `seed 20261121, 250 семейств` (500 примеров, оба направления); public и private - секретные сиды оператора, по 100 семейств
- **Отличие от кампании c1 - данные**: помимо 14 одиночных шаблонов генератор собирает композиционные семейства `chain_store`, `chain_customer`, `chain_month` - два сценария в одном скрипте и связка, джойнящая их выходы (суммы, отношение, день недели, агрегация текста, regex-счет, UPDATE через helper-таблицу). В одном операторе встречается несколько классов расхождений, и правила могут взаимодействовать.
- Состояния данных: s1-s4, тот же генератор warehouse
- Движки: PostgreSQL 16.4, Trino 483 + Iceberg - без изменений
- Арена: архив с SHA-256 `18519eee87328febd8f3f7ea777705bdf2400fbd4610ff9cb05adcc3a8c8a687`
- Исследователь: Hermes в образе `sqltr-researcher:1` (ADR 0007), без интернета; модель Claude Haiku 5.5, усилие Medium; все вызовы через шлюз модели
- Решатель: харнес `sqltr-program` без модели, образ `sqltr-runner:1`; падение кандидата = 0 на примере (ADR 0008)
- Разрешенные изменения: код решателя в `ways/<кандидат>/`
- Таймауты: как в c1 (оператор 30 с, пример 240 с, решатель 120 с)

## Порядок работы

- Кампания уже развёрнута оператором на одной VM: `freeze`, `data`, `journal`, `start` и readiness выполнены. Процедуры арены `prompts/prepare.md` и `prompts/start.md` здесь не применяются: это чужой чек-лист подготовки оператора.
- Чего исследователь НЕ видит - и это норма, а не пробел подготовки: `preparation.md`, `metric.lock.json`, `operator/seeds.json`, каталог `cases/sqltr/campaigns/...` и регистрацию кейса в чекауте арены. Статус журнала (`evaluator.search status`) - единственный критерий готовности наряду с этим файлом.
- Токены API лежат в `/run/secrets/{train,public,private,model}-token`.
- Первым ходом зарегистрируй текущий baseline (`case/ways/baseline`) как кандидат №1: якорная точка кривой.
- **Веди лабораторный блокнот** `ways/hypotheses.md`: гипотеза → изменение → результат каждого шага. Сжатие контекста ничего не должно терять; журнал хранит снимки, блокнот - ход мысли.
- Дальше улучшай решатель: гипотеза - правка - быстрый прогон на подвыборке (`--example-id`) - полный train для каждого предложенного кандидата. Композиционные примеры удобнее разбирать по одному оператору: какой класс расхождения встретился и какое правило должно сработать.
- Пока полный train кандидата не закончился, не предлагай следующий.

## Лимит предложенных решений: 30

Кампания c1 закрыла лёгкий мир за 30 предложений (train 1.0, плато). Здесь мир композиционный: в одном скрипте несколько сценариев и связка; закрывать классы по одному может не хватить - закладывай проверки взаимодействия правил (например, отключить правило и посмотреть, что изменилось на подвыборке). Полный train - 500 примеров, 10-12 минут на кандидата; 30 мест при бюджете шлюза $2.5.

## Сопоставимость замеров

Ключ тот же формат: `split / dataset / subset / conditions`.

| Поле | Значения |
|---|---|
| `dataset` | `train-20261121-250`, `public-v2`, `private-v2` |
| `subset` | `all` - раздел целиком; свои подвыборки называйте сами, в кривую они не входят |
| `conditions` | `sqltr-metric-v2-runner-1` (пакет метрики и образ те же, данные новые) |

Якорь сложности от оператора: решатель-победитель кампании c1 на этом train даёт существенно ниже 1.0 - мир действительно сложнее; baseline ещё ниже. Числа - в preparation-заметках оператора, исследователю не передаются.

## Финализация

- Финалистов на private (K): 5; итоговых решений (N ≤ K): 3
- Выбор финалистов: score на public, устойчивость по направлениям, отсутствие подгонки под примеры
- Перед finalize каждый финалист проходит полный train и public без `candidate_fault`

## Долгие прогоны

По `common/long-runs.md` арены: train запускается отдельным заданием, время ожидания считается по прогрессу; public и private ждутся через `python -m evaluator.client wait`.
