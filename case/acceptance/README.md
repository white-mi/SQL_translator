# Синтетическая приёмка развёртывания

`run.py` поднимает одноразовые train/public/private-оценщики арены, прогоняет через CLI арены мини-кампанию с лимитом 4 и K=2 на синтетических данных (dev-сиды 910001/910002, не сиды оператора) и пишет `report.json`. Журнал, state, токены и данные - свои, в новом каталоге; настоящая кампания не затрагивается.

```bash
python case/acceptance/run.py --arena /opt/arena --work /srv/sqltr-accept-$(date +%s) --runner-image sqltr-runner:1 --local
# без Trino (только PostgreSQL): добавить --directions trino2gp
```

На VM то же делает `sudo bash case/deploy/arena.sh accept`.

## Что проверяется

| ID | Проверка | Почему важно |
| --- | --- | --- |
| A01-A03 | readiness отказывает без журнала; после init - `campaign`, gate включён; public не объявляет защиту private | исследователь не стартует поиск при незащищённом private |
| A04 | пятое предложение при лимите 4 отклоняется | лимит предложенных решений - главная валюта кампании |
| A05 | train возвращает поэкзампларную статистику метрики | на ней исследователь строит гипотезы |
| A06 | `solution.json` выбирает зарегистрированный харнес | реестр харнесов работает |
| A07 | падающий кандидат получает 0 с `candidate_fault`, а не сбой | харнес ADR 0008 |
| A08 | пустой ответ - 0, не ошибка | контракт метрики |
| A09 | public отдаёт только общий score | граница доступа public |
| A10-A13 | private до finalize - отказ; неверный K - отказ; принятый пакет нельзя заменить | отказ до допуска не тратит попытку |
| A14-A15 | API private отдаёт только статус; `record.json` оператора - оценки, победители, допуск | граница доступа private |
| A16 | рестарт сервиса не теряет private; повтор того же пакета идемпотентен | долгие прогоны |
| A17 | падение финалиста не валит серию | единственная private-попытка защищена от кода кандидата |
| A18 | отказ движка валит серию громко, без нулей и победителей | инфраструктурный сбой не превращается в оценку |
| A19 | журнал согласован после кампании | кривая и AUC строятся из него |

Результат локального прогона (песочница, только PostgreSQL): [results/acceptance/local-2026-11-04.json](../../results/acceptance/local-2026-11-04.json) - 19/19 за 273 с. На VM 8.11 с Trino и обоими направлениями: [results/acceptance/vm-2026-11-08.json](../../results/acceptance/vm-2026-11-08.json) - 19/19 за 302 с.

## Стоимость кандидата

`full_train.py` проводит весь train (500 примеров) через арену с настоящими runner и метрикой, в одноразовом каталоге, и замеряет три случая: кандидат с эталонными переводами без кэша метрики (score должен быть ровно 1.0, это заодно проверка всей цепочки), baseline и повтор baseline с кэшем. Скрипт только для оператора: он читает эталоны из `data/train/instances.jsonl`, поэтому в workspace исследователя не попадает (ADR 0009). Результат на VM 8.11: [results/stand/full-train-2026-11-08.json](../../results/stand/full-train-2026-11-08.json).

## Наблюдения из прогона

- Ничья по score между финалистами решается временем решателя (политика `score-direction-known-tokens-asc-seconds-asc-id-asc-v2`): в двух прогонах с одинаковыми кандидатами победитель менялся. Финалисты должны различаться по механизму, а не быть копиями.
- Время на пример в контейнере: решатель ~1.4 с в песочнице и ~0.7 с на VM (в основном старт контейнера), метрика ~0.4 с в песочнице (старт процесса); train-запрос обрабатывает примеры последовательно.
